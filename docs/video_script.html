Part C — The five submission bullets
Full text is in docs/submission_resume_bullets.md. Bullet 5 was rewritten today because the evaluation numbers changed. A recruiter should understand the achievement; an assessor should still see the evidence.
1 — What it does

Built a commute recommender that reads my next Google Calendar event and answers one question: when do I need to leave? It replaces checking three separate apps with a single ranked leave-by time, delivered on a live dashboard and through a REST API.

2 — The data pipeline

Built a pipeline that combines five sources: Google Calendar, OneMap geocoding and routing, LTA live bus arrivals and train alerts, data.gov.sg weather, and a configured origin location. Raw pulls are saved as dated Parquet files and the cleaned data is loaded into a nine-table DuckDB database, where a SQL view ranks up to three routes using window functions and works out the leave-by time, pushing rainy routes with long walks down the ranking.

3 — Making it reliable

Made the pipeline safe to run unattended: failed API calls retry three times with waits of 1, 2 and 4 seconds; re-running ingestion replaces rows instead of duplicating them, proven by unchanged row counts; coordinates are checked against Singapore's bounds; and every run is logged with row counts, duration and errors. Packaged the system as three Docker services sharing one database volume, with all keys and tokens kept out of the image and mounted at runtime.

4 — Finding and fixing a modelling mistake

Found that my first model was mostly copying its own input: it predicted total journey time while being given OneMap's journey time, which carried 87.5% of the model's importance and also capped predictions for long routes. I changed it to predict only the extra delay on top of OneMap's estimate, cutting that input to about 5% and removing the ceiling. I also built bus_headway_gap — the gap between the next bus and the one after it — as a crowding signal feeding a delay model and a bus-crowding model that score all three routes separately.

5 — Measuring whether the model earns its place

Built a daily evaluation that measures the model's average error over a rolling seven days and compares it against using no model at all, with every outcome recording whether it was hand-logged or reconstructed. It currently reports 6.1 minutes against a 10-minute warning threshold, and shows the model is not yet beating the plain routing baseline at 3.7 minutes — a gap I traced to the baseline being scored on reconstructed outcomes derived from its own schedule.

Q&A — backup answers, not part of the recording
Is this a star schema?

Not a formal one, and I would rather say so. route_options is the central fact-like table, one row per commute option with the measures on it, and it has a real foreign key to the calendar event. But weather, bus arrivals and train alerts are time-series snapshots that I join on a natural key and a time window, not proper dimensions with surrogate keys. A real star would need surrogate keys, a date dimension and a consistent grain. Mine is star-shaped, and I designed it around the queries I actually run.

Is actual_min a real journey time?

No, and I am careful with that word. I have no GPS trip tracking, so a true door-to-door time is not observable in this system. Six of my recent outcomes are hand-logged on my phone — real observations, but not GPS. The rest are reconstructed: the schedule, plus the boarding wait I actually saw from the live LTA feed, plus a published headway allowance for rail, plus a penalty when LTA reported a disruption. Every row records which method produced it in actual_source. The crowd label is different — that one is LTA's own observed load, though it is the load of the next bus rather than the exact bus I boarded.

Your model does not beat the baseline. Isn't that a failure?

It is an honest result, and the fact that I can see it at all is the point — I built the baseline comparison into the evaluator so I would find out. Today the model is at 6.1 minutes and the plain OneMap schedule is at 3.7.

But I checked what that comparison is actually made of, and it is not a fair test yet. My model was scored on nine outcomes. The baseline could only be scored on three, because the other six are hand-logged days that have no route row to compare against. And those three reconstructed outcomes were built from OneMap's own scheduled duration, so the baseline is being marked against a number partly derived from itself.

So the correct statement is that I cannot yet show the model earns its place. To settle it I need hand-logged times on journeys that also have a route saved, over more than seven days.

How do you know the model isn't just repeating OneMap?

That is exactly what it was doing in my first version, and I caught it in the feature importances — OneMap's duration was 87.5% of the model, because what I was training on was itself largely derived from that same baseline. So I changed the target. It now predicts the delay on top of the schedule rather than the total, which means the answer is not contained in any single input. That dropped OneMap's importance to about 5%, and the top drivers became rush hour and the two bus-timing features.

Wasn't that just target leakage?

Not in the strict sense. Classic leakage means using a feature that would not exist at prediction time. OneMap's duration does exist before the journey, so using it as an input was not wrong by itself.

The problem was on the target side. My synthetic bootstrap and my reconstructed outcomes were themselves largely built from that same OneMap baseline, so the target was mostly a function of one of the inputs. The model re-derived OneMap's number instead of learning the delay around it. The accurate name is target-proxy dominance, or circular target construction — not leakage. Predicting the residual breaks the circle: the target becomes what the baseline fails to account for.

What is model drift and how do you detect it?

Three kinds. Data drift is when the inputs change — my commute hour shifting from 8 AM to 10 AM. Concept drift is when the relationship changes — a new MRT line opens and the same hour now means a shorter journey. Training-serving skew is when a feature is computed differently in training than in production, like a rain flag encoded as true/false one side and 1/0 the other. My main signal is the rolling 7-day error against a 10-minute threshold, because a rising error is a symptom of all three. Per-feature statistical tests like PSI could be added later.

Why Random Forest and not linear regression?

Rush hour combined with rain does not behave like rush hour plus rain, and a forest picks up that interaction without me hand-building it. It also copes with a small dataset, which matters because I am still bootstrapping with synthetic rows until enough real journeys accumulate.

Why batch and not streaming with Kafka?

Nothing in my data moves fast enough to need it. Bus arrivals refresh every couple of minutes and weather every two hours. Airflow runs the batch every 30 minutes and my own scheduler polls adaptively when an event is close. Kafka would add brokers, partitions and consumer groups for no benefit at this data rate.

Why did routing fail for your October event?

OneMap will not route to a date that far ahead. I tested the same origin and destination across different dates: today returns three itineraries, a week out returns two, two to four weeks out returns one, and about two months out returns HTTP 400 with nothing. My October event is 59 days away, so it gets no routes. It is also a video consultation, so it has no physical address to geocode, and the pipeline falls back to my configured work address. That fallback is deliberate, but the honest answer is that the system needs a near-term event with a real address to produce a full three-route recommendation.

What would you change if this scaled to many users?

For high-throughput batched inference I would move the model behind something like Triton instead of FastAPI, and switch pandas for a GPU dataframe library if the data grew a lot. But the Day 5 technology selection exercise maps a low-traffic prediction API to FastAPI and around 100 MB of daily data to pandas, which is exactly what I built. Knowing when not to reach for a tool matters as much as knowing how to use it.

How does the geocoder handle messy addresses?

It tries in order: a six-digit postal code pulled out of the text, which geocodes almost perfectly on OneMap; then the full address; then the address with ", Singapore" removed; then just the first part before a comma. The word-boundary check stops it matching a seven-digit phone number. And if every candidate fails, it falls back to my configured work address rather than crashing — which is what happened with the video-consultation event.
