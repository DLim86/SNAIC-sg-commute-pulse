System Architecture — 3 Layers
1:10 → 2:20 · ~150 words
Screen / Do
  • Open docs/roadmap.html in browser
  • Point at each of the 3 phases as you name them
Say

The system has three layers, and I separated them because they solve different problems.

Layer one is the batch pipeline — it fetches the data sources, stores them in DuckDB, and runs a SQL transformation. That’s the core data engineering work.

Layer two is ML — a Random Forest predicts delay on top of the routing engine’s schedule, and a second predicts bus crowding.

Layer three is serving — Streamlit, refreshing every 60 seconds, and a FastAPI layer exposing the same data as REST endpoints.

For storage, I land the raw pulls as partitioned Parquet under data/raw, then load the cleaned, typed version into DuckDB — that’s what the dashboard and API actually query.

Optional — only if ahead of time

Why two storage layers at all: Parquet is cheap append-only file storage that keeps what each API gave me, and DuckDB is a columnar analytical engine that makes the joins and window functions fast. Different jobs, so I kept them separate.

On the schema: route_options is the central table with the measures — duration, walking distance, transfers, fare — and a real foreign key to the calendar event. Weather, bus arrival and train alert tables join on a natural key and a time window instead, so it's star-shaped around route_options but not a formal dimensional star schema — no surrogate keys, no date dimension.

Say

This is the batch pipeline, and there’s one part here I especially want to show you.

I wrote an Airflow DAG with seven tasks in a chain: schema check, ingest, transform, predict, backfill, a gate, and evaluate. The gate is a ShortCircuitOperator that only lets the daily model evaluation through on the 08:00 run, not every 30-minute tick.

Every API call goes through a retry wrapper with exponential backoff — three attempts, and the wait doubles each time: one second, then two, then four. LTA’s API does return errors during rush hour, and without that, one blip at 8 AM would kill the whole run.

Now the part I want to highlight. I made the ingestion safe to rerun. If the pipeline dies halfway, I don’t want the next run to duplicate everything, so every ingestion write is an upsert — the same record is replaced instead of inserted twice. That’s what makes the ingestion idempotent, and it’s the property that lets me run this on a schedule without watching it.

I can show you that it actually holds. Here are the row counts. I run the ingestion again — same counts. The one table that does grow is bus arrivals, and that’s deliberate — the fetch timestamp is part of its primary key, because I want to keep those as a time series rather than overwrite them.

Before anything goes into DuckDB I also write the extracted records out to date-partitioned Parquet as a staging layer — one file per source per day, not a full replayable archive of the raw API responses. That’s honestly on my list to fix.

Optional — only if ahead of time

On idempotency specifically: DuckDB's INSERT OR REPLACE matches on the primary key, so the key choice is the design. route_options and route_legs are keyed on option_id, so a re-run replaces them and the row counts are unchanged — that is the verification. bus_arrivals includes fetched_at in the key, so a re-run deliberately appends a new snapshot rather than overwriting the time series. Same statement, deliberately different behaviour.

On data quality: coordinates are bounds-checked against Singapore (lat 1.15–1.47, lng 103.6–104.1) before they reach DuckDB, because OneMap returns (0, 0) for an address it cannot resolve, and every run — success or failure — is written to the pipeline_runs monitoring table with row counts, duration and error text.

Say

The transformation layer is a SQL view, v_enriched_routes, joining route options to destination weather and any active train alerts.

The leave-by time is event start minus journey duration minus a 10-minute walking buffer.

Ranking is a window function: ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY penalty, duration). The penalty is more than just “pick the fastest” — a rainy route with over 400 metres of walking gets pushed down even if it’s quicker.

The “why chosen” line is SQL too — nine reasons, worked out with MIN() OVER (PARTITION BY event_id) against the other routes.

Disruption warnings are filtered to the rail lines the route uses, so a bus-only route shows none.

This is the live output layer — refreshing every 60 seconds, re-querying DuckDB with no external API calls.

There’s a database problem I hit twice here, worth explaining. DuckDB allows one writer at a time. My first version cached the connection at startup, so the dashboard never saw new rows at all. Removing the cache wasn’t enough — the script then held that connection open while sleeping for 60 seconds, blocking the pipeline’s writes for almost the entire minute. The fix was to run every query up front, close the connection, and only then render and sleep — open for milliseconds instead of a minute. Tested both ways: the old pattern throws a lock error on write, the new one doesn’t.

Optional — only if ahead of time

The two bugs in order. First, @st.cache_resource caches the decorated function's return value across every rerun in the process, so the connection object — and the snapshot it was holding — never changed. Removing it fixed staleness. Second, the connection was still open during time.sleep(60), which blocked the writer. Draining every query into memory before rendering fixed that. Two different bugs with the same symptom.

Say

There are two models here, and I want to spend most of this section on one design decision and one feature.

First the design decision. My first model predicted the total journey time, using OneMap’s own duration as one of its inputs — and that single input accounted for 87% of the model. It was mostly re-deriving OneMap’s estimate, not learning delay, and because a Random Forest can’t predict outside its training range, every route capped out at the same value regardless of how long it really was.

So I changed what the model predicts: the delay on top of OneMap’s schedule, not the journey from scratch. The number you see is the baseline plus the predicted delay. That fixed both problems — the baseline’s importance dropped from 87% to about 5%, and the prediction ceiling disappeared, because the total is anchored to OneMap’s figure.

Now the feature I’m most pleased with. LTA’s arrival API gives you the next bus and the one after it. I originally stored that second time only for the display. Later I realised the gap between those two times was itself a signal, so I engineered bus_headway_gap: next_bus2_mins minus next_bus_mins. A wide gap means the service is running irregularly, so passengers have had longer to build up, and the bus that arrives is fuller — even when the first arrival time looks identical to a well-spaced service. That feeds both models, and all three route options are scored individually.

Then the MLOps loop: train, predict, backfill, evaluate, drift check. For the last seven days I manually logged my own departure and arrival times on my phone — those are real observations, just not GPS-tracked. Other backfilled rows are a reconstruction instead: schedule plus observed boarding wait, or a published headway allowance. actual_source keeps the two types separate, so one is never mistaken for the other.

The evaluator runs daily and computes a rolling seven-day MAE once at least seven pairs exist. With those seven hand-logged days, it computes a real number — 16.3 minutes — above my 10-minute threshold, so the dashboard raises a genuine warning. With only seven observations, I treat that as a warning signal, not proof that concept drift has definitely occurred.

Optional — only if ahead of time

The delay model uses 13 features: base_duration, next_bus_mins, next_bus2_mins, bus_headway_gap, walk_distance_m, num_transfers, is_rainy, rain_exposure, rush_hour, is_weekend, hour_of_day, day_of_week, bus_crowd_score. Measured importances on the currently trained model (random_state=42; the exact digits shift a little as real rows join the synthetic bootstrap): rush_hour 0.36, next_bus2_mins 0.17, next_bus_mins 0.14, rain_exposure 0.12 — and base_duration only 0.05, which is the point. Outcome reconstruction: BUS uses the observed boarding wait from the live LTA feed; MRT and LRT add a published headway allowance plus 20 minutes if a HEAVY disruption was active; walking routes are deterministic. Each row stores which method was used in actual_source.

Q&A Reference — Not part of the recording script · expand for backup answers
If asked: Is this a star schema?

Not a formal one, and I'd rather say so. route_options is the central fact-like table — one row per commute option, with the measures on it — and it has a genuine foreign key to calendar_events, which acts as the event dimension. But weather_forecast, bus_arrivals and train_alerts are time-series snapshots that I join on a natural key and a time window, not conformed dimensions with surrogate keys. A real star would need surrogate keys, a date dimension and a consistent grain. Mine is star-shaped, and I designed it around query patterns rather than around dimensional modelling rules.

If asked: Is actual_min a real journey time?

No, and I’m careful about that word. I have no GPS trip tracking, so a true door-to-door time isn’t observable in this system. What I store is a reconstructed outcome estimate: OneMap’s scheduled duration, plus the wait that was genuinely observed at the boarding stop from the live LTA feed, plus a published headway allowance for rail where there’s no live feed, plus a disruption penalty when LTA reported one. Each row records which method produced it in actual_source. The crowd label is different — that one is a real observation, LTA’s Load field, though it’s the load of the next bus rather than the exact bus I boarded.

If asked: How do you know the model isn’t just repeating OneMap?

That’s exactly what it was doing in my first version, and I caught it in the feature importances — OneMap’s duration accounted for 87.5% of the model, because the target I was training on was itself largely derived from that same baseline. So I changed the target. It now predicts the delay on top of the schedule rather than the total, which means the target isn’t contained in any input. That dropped the baseline’s importance to about 5%, and the top drivers became rush hour and the two bus-timing features. The evaluation also computes the error of the plain OneMap schedule alongside the model’s, so I can see directly whether the model is earning its place.

If asked: Wasn’t that just target leakage?

Not in the strict sense, and I’d rather be precise about it. Classic target leakage means a feature that would not be available at inference time. OneMap’s duration is available at inference time — I have it before the journey starts — so using it as an input was not inherently invalid.

The real problem was on the target side. My synthetic bootstrap and my reconstructed outcomes were themselves heavily derived from that same OneMap baseline, so the target was largely a function of one of the inputs. The model dutifully re-derived OneMap’s number instead of learning the delay around it, and base_duration came out at 0.875 importance. The accurate name for that is target-proxy dominance, or circular target construction — not leakage.

Predicting the residual over the baseline breaks the circularity: the target is now what the baseline fails to account for. base_duration dropped to about 0.05 and the top drivers became rush hour and the two bus-timing features. It also removed the prediction ceiling, since the total is anchored to OneMap’s figure rather than bounded by the training range.

If asked: What is model drift? How do you detect it?

Three types from Day 4: Data drift — input feature distributions change (e.g. my commute hour shifts from 8 AM to 10 AM). Concept drift — the relationship between features and target changes (e.g. a new MRT line opens; same hour now predicts shorter journey). Training-serving skew — a feature is computed differently in training vs. production (e.g. is_rainy encoded as True/False in training but 1/0 in the pipeline). My primary signal is the 7-day MAE threshold — rising MAE is a symptom of all three regardless of root cause. Statistical tests like PSI or KS-test per feature can be added later.

If asked: Why Random Forest and not Linear Regression?

Random Forest handles non-linear interactions — rush hour combined with rain has a different effect than either alone. Linear Regression would require manual feature engineering for that. RF also handles small datasets gracefully, which matters because I'm bootstrapping with synthetic data until enough real runs accumulate.

If asked: Why batch processing and not real-time streaming (Kafka)?

Bus arrival data refreshes every 2 minutes. Weather updates every 2 hours. Airflow runs the batch DAG every 30 minutes; the Docker scheduler adaptively polls for live snapshots — nothing changes faster than that. Kafka would add infrastructure complexity (brokers, consumer groups, partitions) with no benefit at this data velocity.

If asked: What would you do differently if the system scaled to many users?

Replace FastAPI with NVIDIA Triton Inference Server for high-throughput batched ML inference; replace pandas with cuDF from the RAPIDS ecosystem for GPU-accelerated data processing; add Metabase as a BI dashboard for non-technical staff. But the Day 5 Technology Selection Exercise maps "low-traffic prediction API" to FastAPI and "100MB daily data" to pandas — which is exactly what I built. Knowing when not to use a tool is as important as knowing how to use one.

If asked: How does the geocoder handle varied address formats?

Progressive fallback: (1) extract a 6-digit postal code with re.findall(r'\b\d{6}\b', address) — postal codes geocode with near-perfect accuracy on OneMap; (2) full address string; (3) address with ", Singapore" stripped; (4) first comma-delimited token. Word boundary \b prevents matching 7-digit phone numbers.

If asked: Why is the 7-day MAE so high (16.3 min)?

Two things are compounding. First, the sample is tiny — 7 manually-logged days, not weeks — so a couple of unlucky commutes move the average a lot. Second, I cross-checked one of my own routes against Google Maps at the same departure time (Tuesday 9 AM) and found OneMap's stored duration for the Punggol NE-line-plus-bus-100 itinerary is 38 minutes, while Google's own itinerary for the identical route — same stations, same bus — comes out at 53–55 minutes. That's a roughly 15–20 minute gap in the baseline schedule itself, before my model even adds a delay on top. So some of what the drift warning is catching is probably OneMap's own duration estimate running optimistic for this route, not just my model being wrong. I'd want more days of data before concluding that firmly, but it's a lead I'd chase first if I kept working on this.

If asked: How does the stale event fix work?

After ingest, _purge_stale_events(con, event_id) deletes all future calendar_events rows whose primary key is not the current active event_id, along with their route_options and route_legs children. Cascading delete order: route_legs first (FK child), then route_options, then calendar_events. Without this, a rescheduled event leaves both the old and new start_time in the DB and transform picks whichever appears first.
