Data Sources · Source System 1
Google Calendar Input & Geocoding
Fetch the user's next upcoming calendar event with a location via the Google Calendar API (OAuth2). Geocode the location into GPS coordinates using OneMap. This is the pipeline's entry point — it drives all downstream routing, bus, and weather lookups.
Google Calendar API OAuth2 OneMap Search API google-api-python-client 
# scripts/ingest.py — fetch next real event from Google Calendar
from google.oauth2.credentials import Credentials
from google_auth_oauthlib.flow import InstalledAppFlow
from googleapiclient.discovery import build

SCOPES = ["https://www.googleapis.com/auth/calendar.readonly"]

def fetch_next_calendar_event(con, token):
    creds = Credentials.from_authorized_user_file("token.json", SCOPES)
    service = build("calendar", "v3", credentials=creds)

    events = service.events().list(
        calendarId="primary",
        timeMin=datetime.now(timezone.utc).isoformat(),
        maxResults=10, singleEvents=True, orderBy="startTime"
    ).execute().get("items", [])

    for event in events:
        location  = event.get("location", "").strip()
        start_dt  = event.get("start", {}).get("dateTime")
        if not location or not start_dt:
            continue  # skip all-day / locationless events
        lat, lng = geocode(location, token)
        event_id = f"GCAL_{event['id']}"
        con.execute("""INSERT OR REPLACE INTO calendar_events
            (event_id, title, start_time, location_raw, dest_lat, dest_lng)
            VALUES (?, ?, ?, ?, ?, ?)""",
            [event_id, event.get("summary", "Untitled"), start_dt, location, lat, lng])
        return event_id, lat, lng

    raise ValueError("No upcoming events with a Singapore location found")

# scripts/ingest.py — Flatten OneMap route response
def fetch_routes(origin_lat, origin_lng, dest_lat, dest_lng, token, event_id):
    r = requests.get(
        "https://www.onemap.gov.sg/api/public/routingsvc/route",
        params={"token": token, "start": f"{origin_lat},{origin_lng}",
                "end": f"{dest_lat},{dest_lng}", "routeType": "pt",
                "mode": "TRANSIT", "numItineraries": 3}
    ).json()
    rows = []
    for i, it in enumerate(r.get("plan", {}).get("itineraries", [])):
        rows.append({
            "option_id": f"{event_id}_opt{i}", "event_id": event_id,
            "total_duration_min": it["duration"] // 60,
            "walk_distance_m": it["walkDistance"],
            "num_transfers": it["transfers"],
            "fare": it.get("fare", 0),
        })
    return pd.DataFrame(rows)

Data Transformation
SQL Cleaning, Recommendation Logic & Walk Alternative
Join routes, weather, and alerts into a ranked recommendation. Calculate leave-by time, flag rainy walks, detect MRT disruptions, and rank routes using window functions. The recommendation_reason field has 9 dynamic labels (e.g. "✓ Fastest + direct", "✓ Fewest transfers (N)", "✓ Least walking (Xm)", "⚠ Rain — Xm exposed walk") computed via MIN() OVER (PARTITION BY event_id) window functions — not hardcoded. Weather and disruption warnings appear under "Why chosen:" for the recommended route. Disruption status is filtered to the actual rail modes in the route (MRT-only route shows MRT disruptions only, not MRT/LRT). Output includes: inline first-transit live arrival after the step-by-step legs (X1+X2 for bus; headway estimate ~3-5 min for MRT, ~5-10 min for LRT — no public real-time MRT/LRT arrival API in Singapore), an alt routes section labelled "Other route options (sorted by arrival time)" with [2]/[3] labels (always exactly 2 alternatives — OneMap API hard-caps at 3 total itineraries), consecutive MRT+LRT legs grouped in compact display, per-alt first-transit X1 + disruption note, and a walk alternative with Zone 1/2 health stats plus optional Garmin/Whoop fitness context. Note: alt routes query route_options directly — the view's weather join and ranking are not needed for the alternatives. An earlier version of the view joined the globally-latest weather row, which matched all 47 areas and returned 47× duplicates; the join is now scoped to the event's own nearest_weather_area.
SQL JOINs CASE WHEN Window functions INTERVAL arithmetic CREATE VIEW Garmin API (optional, off) Whoop API (optional, off) inline live arrival alt routes [2]/[3] dynamic reason labels dynamic disruption filter 
-- scripts/transform.sql — Core recommendation view

CREATE OR REPLACE VIEW v_enriched_routes AS
SELECT
    r.option_id, r.event_id, r.total_duration_min,
    r.walk_distance_m, r.num_transfers, r.fare,
    e.start_time, e.title, e.dest_lat, e.dest_lng,

    -- When to leave (10 min buffer)
    e.start_time - INTERVAL (r.total_duration_min + 10) MINUTE AS leave_by,

    w.forecast AS weather_forecast,
    w.is_rainy,
    CASE WHEN ta.alert_id IS NOT NULL THEN ta.message ELSE NULL END AS alert_msg,

    -- Recommendation label (abbreviated here — 9 branches in schema.py)
    CASE
        WHEN w.is_rainy AND r.walk_distance_m > 400
            THEN '⚠ Rainy — take covered transport'
        WHEN ta.alert_id IS NOT NULL
            THEN '⚠ MRT disruption — add 20 min buffer'
        WHEN r.total_duration_min = MIN(r.total_duration_min)
                OVER (PARTITION BY r.event_id)
            THEN '✓ Fastest option'
        ELSE 'Alternative route'
    END AS recommendation_reason,

    -- Rank routes per event (1 = best)
    ROW_NUMBER() OVER (
        PARTITION BY r.event_id
        ORDER BY
            CASE WHEN w.is_rainy AND r.walk_distance_m > 400 THEN 1 ELSE 0 END,
            r.total_duration_min
    ) AS route_rank

FROM route_options r
JOIN calendar_events e ON r.event_id = e.event_id
-- Destination-specific: the event's own weather area, latest row for THAT area.
-- Joining on the globally-latest fetched_at matched all 47 areas (47x rows).
LEFT JOIN weather_forecast w
    ON w.area = e.nearest_weather_area
   AND w.fetched_at = (
       SELECT MAX(fetched_at) FROM weather_forecast ww
       WHERE ww.area = e.nearest_weather_area
   )
LEFT JOIN train_alerts ta
    ON ta.severity = 'HEAVY'
   AND ta.fetched_at > NOW() - INTERVAL '30 minutes';

Streamlit Dashboard
A read-only Streamlit dashboard that queries DuckDB and shows the top commute recommendation for the next calendar event. The dashboard auto-refreshes every 60 seconds using time.sleep(60); st.rerun(). It shows: an event card with a countdown to leave-by time; a 3-column metrics panel (leave by / journey time / fare); a "Why chosen" info block; conditional weather and train disruption warnings; step-by-step legs with mode icons; inline live bus arrivals with actual HH:MM clock times and X2 miss-it arrival; estimated MRT/LRT headways with a caveat that no public real-time MRT API exists; alt route expanders [2] and [3] with compact leg tokens and first-transit X1 clock times; and an ML prediction panel that shows predicted duration, crowd level, and 7-day MAE. Critical — two separate bugs with the same symptom. (1) The connection was cached with @st.cache_resource, so the same connection object — and its snapshot — was reused on every rerun and new pipeline rows were never visible. The decorator was removed; a fresh duckdb.connect(DB_PATH, read_only=True) now opens each rerun. (2) That connection was still open during time.sleep(60), so the reader blocked the pipeline's writer for almost the whole minute. Every query the page needs is now run up front and the connection is closed in a finally block before anything renders or sleeps — open for milliseconds, not a minute.

Production Quality · Day 2
Retry, Idempotency & Data Quality
The LTA API times out during rush hour. The OneMap token expires silently. A double-run creates duplicate rows. Add three things to every API call: exponential backoff retry, INSERT OR REPLACE so re-runs are safe, and coordinate validation that rejects bad GPS data before it reaches DuckDB.
retry + backoff INSERT OR REPLACE coord validation pipeline_runs log 
# scripts/ingest.py — wrap every requests.get() in this function
import time, logging

def fetch_with_retry(url, headers=None, params=None, max_retries=3):
    for attempt in range(max_retries):
        try:
            resp = requests.get(url, headers=headers, params=params, timeout=10)
            resp.raise_for_status()
            return resp.json()
        except requests.RequestException as e:
            if attempt == max_retries - 1: raise
            wait = 2 ** attempt  # 1s → 2s → 4s (exponential backoff)
            logging.warning(f"Attempt {attempt+1} failed. Retrying in {wait}s")
            time.sleep(wait)

# Validate GPS is inside Singapore before inserting
def validate_sg_coords(lat, lng):
    if not (1.15 <= lat <= 1.47 and 103.6 <= lng <= 104.1):
        raise ValueError(f"Coords ({lat}, {lng}) outside Singapore bounds")

# Idempotent insert — safe to re-run, no duplicates
con.execute("""
    INSERT OR REPLACE INTO weather_forecast
    SELECT * FROM staging_weather
""")

Why each matters
Retry/backoff — LTA returns 429 or 500 during peak hours. One failure kills the run without retry.
Idempotency — If the pipeline crashes halfway and restarts, INSERT OR REPLACE prevents duplicate rows. Verified, not assumed: re-running ingestion leaves route_options and route_legs row counts unchanged, because both are keyed on option_id. bus_arrivals intentionally grows on every run — fetched_at is part of its primary key, so each run appends a new snapshot instead of overwriting the time series. Same SQL statement, deliberately different behaviour, and the key choice is what decides which.
Coord validation — OneMap returns (0, 0) for unresolved addresses. A bus stop in the Indian Ocean corrupts all downstream recommendations.

Raw Data Zone · Day 2
Parquet as Intermediate Storage
Before loading into DuckDB, write the extracted records to Parquet in a date-partitioned landing zone. This separates ingestion from transformation and gives a file-level record of what a run collected. Be precise about what this layer is. It holds the records extracted from each API, not the untouched payloads, and save_parquet() writes one file per source per day — a second run on the same day overwrites it. So it is a staging layer holding the latest snapshot per source per day. That is enough to fix a bug in the SQL and re-run the transformation against that snapshot without re-calling the APIs, and it is not enough to replay an arbitrary earlier run or to serve as a point-in-time audit trail. A true raw archive would keep every response keyed by fetch timestamp; that is listed as future work, not claimed here.
Parquet columnar storage date partitioning raw zone read_parquet 
# scripts/ingest.py — save raw before loading to DuckDB
from pathlib import Path
from datetime import date

def save_raw_parquet(df, source_name):
    today = date.today().isoformat()          # e.g. "2026-07-15"
    path = Path(f"data/raw/{source_name}/date={today}")
    path.mkdir(parents=True, exist_ok=True)
    out = path / f"{source_name}_{today}.parquet"
    df.to_parquet(out, index=False, compression="snappy")
    return out

# Use it in your ingestion flow:

""")

from fastapi import FastAPI, HTTPException
import duckdb

app = FastAPI(title="SG Commute API", version="1.0")

def get_db():
    return duckdb.connect("db/commute.duckdb", read_only=True)

@app.get("/health")
def health():
    return {"status": "ok"}

@app.get("/api/v1/recommendation/{event_id}")
def get_recommendation(event_id: str):
    rows = get_db().execute("""
        SELECT event_id, title, leave_by, total_duration_min,
               fare, weather_forecast, is_rainy, alert_msg,
               recommendation_reason
        FROM v_enriched_routes
        WHERE event_id = ? AND route_rank = 1

@app.get("/api/v1/pipeline/status")

    return get_db().execute("""
        SELECT source, status, rows_upserted, ran_at
        FROM pipeline_runs ORDER BY ran_at DESC LIMIT 10
    """).df().to_dict(orient="records")

Orchestration · Day 2
Airflow Pipeline DAG
Replace manual script execution with a scheduled DAG. Airflow is the orchestration layer: it defines the pipeline as a task graph — what runs, in what order, when to retry on failure, how often to schedule. Running locally with airflow standalone gives a web UI showing which tasks succeeded or failed, with per-task logs. The actual DAG is a 7-task sequential chain with a ShortCircuitOperator that gates the daily evaluation task to the single run whose logical time is 08:00 SGT — it checks hour and minute, because on a 30-minute schedule an hour-only test fires twice. Airflow and the Docker scheduler.py are two alternative orchestration paths over the same scripts, not two layers running together: DuckDB permits one writer, so only one of them runs at a time.
Apache Airflow DAG BashOperator ShortCircuitOperator 7-task sequential chain airflow standalone 
# dags/commute_pipeline_dag.py
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta, timezone
from airflow.operators.bash import BashOperator
from airflow.operators.python import ShortCircuitOperator

PROJECT_DIR   = str(Path(__file__).parent.parent)
SGT           = timezone(timedelta(hours=8))
EVAL_HOUR_SGT = 8

def _is_evaluation_window(**ctx):
    # Uses the DAG run's LOGICAL time, not wall clock, so a delayed or
    # re-run task still evaluates for the interval it was scheduled for.
    # The minute check is what makes it once-daily: on a */30 schedule an
    # hour-only test passes at BOTH 08:00 and 08:30 — the original bug.
    logical = ctx.get("logical_date") or ctx.get("data_interval_start")
    if logical is None:
        logical = datetime.now(timezone.utc)
    if logical.tzinfo is None:
        logical = logical.replace(tzinfo=timezone.utc)
    local = logical.astimezone(SGT)
    return local.hour == EVAL_HOUR_SGT and local.minute < 30

with DAG(
    dag_id="commute_pipeline",
    schedule="*/30 * * * *",       # every 30 minutes
    start_date=datetime(2026, 6, 1),
    catchup=False,
) as dag:

    schema_check    = BashOperator(task_id="schema_check",    bash_command=f"cd '{PROJECT_DIR}' && python scripts/schema.py")
    ingest          = BashOperator(task_id="ingest",          bash_command=f"cd '{PROJECT_DIR}' && python scripts/ingest.py")
    transform       = BashOperator(task_id="transform",       bash_command=f"cd '{PROJECT_DIR}' && python scripts/transform.py")
    predict_commute = BashOperator(task_id="predict_commute", bash_command=f"cd '{PROJECT_DIR}' && python scripts/model.py --predict")
    backfill_actuals= BashOperator(task_id="backfill_actuals",bash_command=f"cd '{PROJECT_DIR}' && python scripts/model.py --backfill")
    gate_evaluate   = ShortCircuitOperator(task_id="gate_evaluate", python_callable=_is_evaluation_window)
    evaluate_model  = BashOperator(task_id="evaluate_model",  bash_command=f"cd '{PROJECT_DIR}' && python scripts/model.py --evaluate")

    # gate_evaluate passes for exactly one run per day — the */30 run whose
    # logical time is 08:00 SGT. Every other run short-circuits here.
    schema_check >> ingest >> transform >> predict_commute >> backfill_actuals >> gate_evaluate >> evaluate_model

Docker Compose — three runtime services
Package the entire system into three Docker containers: the pipeline, the FastAPI server, and the Streamlit dashboard. With a single docker compose up, anyone can run the full system on any machine without installing Python or configuring anything. The DuckDB file is volume-mounted so data persists across restarts. The pipeline service runs scripts/scheduler.py — a 7-state adaptive machine (NO_EVENT → EVENT_DETECTED_BURST → WATCHING → LEAVE_WINDOW → IN_TRANSIT → ARRIVAL_VERIFY → POST_ARRIVAL_COOLDOWN) that bounds every polling burst, never calls expensive APIs every second, and sleeps up to 1 hour when there is no upcoming event. This replaces the old fixed 30-minute sleep loop. Three runtime services, not four: Airflow is an alternative orchestration path over the same scripts, not a fourth container running alongside. DuckDB permits a single writer, so either the Docker scheduler drives the pipeline or Airflow does — never both at once.

Data Modelling, Lake vs Warehouse & dbt
Day 3 covers the conceptual layer beneath your pipeline: how to model data, where to store it, and how industry uses dbt to bring structure to SQL transforms. Your project already implements all of these patterns — this station shows you how to name and explain them confidently in your video.
Star-shaped schema Data Lake Data Warehouse dbt concepts Type-1 upsert (reference data) Data Lineage
Your project = Data Lake + Data Warehouse
Landing zone — data/raw/ Parquet files. Holds the records extracted from each API (not the untouched payloads), date-partitioned, one file per source per day. A same-day re-run replaces that file, so this is a staging layer rather than a replayable archive.
Data Warehouse — db/commute.duckdb. Cleaned, typed, relational schema. Queried by dashboards and APIs.
Transactional DB (not us) — Postgres / MySQL stores live app state row-by-row. DuckDB is columnar-analytical — designed for reads and aggregations, not write-heavy app workloads.
Your DuckDB schema = star-shaped, not a formal star
Fact table — route_options: each row is one commute option. Has measurable facts: duration_min, fare, walk_distance_m.
Dimension tables — weather_forecast, bus_arrivals, train_alerts: descriptive context that joins to routes via time or service_no.
Type-1 upsert (reference data) — INSERT OR REPLACE overwrites the previous row for the same key, so the 8am weather reading is replaced by the 10am one. Not applied uniformly: bus_arrivals puts fetched_at in its primary key on purpose, so live arrivals append as a time series instead of overwriting.
dbt vs our transform.py — same goal, different tool
Our approach (transform.py)          dbt equivalent
────────────────────────────         ──────────────────────────────────────

Both produce the same output: clean joined data ready for serving. dbt adds governance and structure at the cost of a new tool. For a project this size, transform.py is a valid and common production choice.
Why NOT Kafka / Flink here
Kafka is for data that changes every second — click streams, payments, IoT sensors. Bus arrival data refreshes every 2 minutes; weather every 2 hours. A 30-minute Airflow batch schedule is perfectly adequate.
Flink processes Kafka streams with stateful windowing. No Kafka stream → no Flink. Airflow covers our orchestration needs entirely.
Why NOT Spark / PySpark here
Spark is designed for TB-scale data across a distributed cluster. Our dataset: ~50 route rows per run, ~5,000 bus stops, ~47 weather areas. Spark's startup and shuffle overhead would dwarf actual processing time.
DuckDB handles GB-scale analytical queries on a single machine in milliseconds. It is the correct tool choice for a pipeline of this size.

MLOps · Rubric Criterion 2 · 30 marks
Commute Delay Predictor & Model Evaluation
The rubric awards 30 marks for ML and Real-Time Output: batch processing, model training and inference, and a live refreshed dashboard. The pipeline already handles batch and the dashboard — this station adds the models. The regressor does not predict total journey time. It predicts the delay on top of OneMap's scheduled duration (predicted_total = OneMap baseline + predicted delay), and a second classifier predicts bus crowding. Both are evaluated daily via Airflow, and predictions appear live on the Streamlit dashboard.
Why the target changed — residual, not total
The first version predicted the total journey time, with OneMap's own duration as one of the inputs. Two things went wrong at once.
1 · The baseline dominated the model. base_duration reached 0.875 feature importance. Using an available baseline prediction as a feature is not automatically invalid — OneMap's estimate is known at inference time. The problem was the target: the synthetic bootstrap and the reconstructed outcomes were themselves largely derived from that same baseline, so the model was re-deriving OneMap's number rather than learning the contextual delay around it. That is target-proxy dominance from circular target construction, not a case of an unavailable-at-inference feature leaking in.
2 · A hard prediction ceiling. A Random Forest cannot predict outside its training range, so every long route collapsed to the same capped value.
The fix: predict delay_min — the residual over the baseline — instead of the total. base_duration importance dropped from 0.875 to about 0.041, and the ceiling disappeared because the total is now anchored to OneMap's figure: a 125-minute route stays a 125-minute route, plus a delay.

Data bootstrap — fix for limited history
The pipeline may only have a few days of real data at demo time. _bootstrap_synthetic_duration() generates 500 rows whose target is delay_min, driven by live context rather than by the baseline:
• Waiting for the visible bus → +0.6 × next_bus_mins
• bus_headway_gap > 8 (bunched service) → +4 min
• Rush hour → +6 + 0.05 × base_duration
• Rain → +4 + walk_distance_m / 400
• Weekend → −3 min  ·  each transfer → +2.5 min  ·  full bus (LSD) → +3 min
Blended with real rows and re-fit as real data accumulates.
Stated honestly: these rows are generated from documented commuting patterns, are never written to the database, and are not observations. They exist so the model produces sensible output before real outcomes accumulate.

Shadow → Canary → Promote
Shadow — new model sees same live inputs, predictions logged only, never shown to users. Zero risk.
Canary — gradually shift real traffic: 95%/5% → 50%/50% → 100%/0%. Pause if error rate or latency spikes.
Promote — if challenger MAE beats production by >5%, set @champion alias. Old production → archived (rollback available).
Rollback — reassign @champion alias to any prior version. Serving code unchanged.
MLflow vs pipeline_runs — different concerns
pipeline_runs — "ingest ran at 08:10, 47 rows, success". Tracks pipeline health, not model experiments.
MLflow — "training run #7 used n_estimators=100, mae=4.2 min, 520 rows, 2026-07-01". Tracks ML experiment history and artifact lineage. Two separate concerns, two separate tools.
Three Drift Types (Day 4)
Data Drift — input feature distributions change. Example: user changes jobs, hour_of_day shifts from 8 AM to 10 AM starts.
Concept Drift — feature-to-target relationship changes. Example: a new MRT line opens, so the same rush_hour and bus_headway_gap now imply a smaller delay_min than they did during training.
Training-Serving Skew — feature computed differently in training vs production. Example: is_rainy encoded as True/False at training time but 1/0 in production — model was never trained on these values.
Monitoring: Prometheus + Grafana

Model logs — model_uri, feature_version, input_features (JSON), prediction_value, inference_duration_ms. Grafana dashboards visualise these alongside MAE over time.
Together: system health (Prometheus/Grafana) + model health (MAE from predictions table) = full observability.

RAPIDS ecosystem — when you'd actually use it
cuDF — GPU DataFrame (pandas API). Use when data is GB-scale and pandas becomes the bottleneck. Not our scenario: we process ~50 rows per run.
cuML — GPU-accelerated ML (scikit-learn API). Use when model training takes hours due to dataset size. Our Random Forest trains in under 1 second on CPU.
Dask-cuDF — distributed GPU DataFrames across a cluster. Use for TB-scale ETL. Overkill for 47 weather rows.
CuPy — NumPy replacement on GPU. Use when numerical computation is the bottleneck. Our bottleneck is API latency, not computation.
Triton vs FastAPI — what the choice actually means
FastAPI — Python ASGI server. Calls model.predict() directly. Startup in 1s. No GPU required. Correct for <100 predictions/min.
Triton — NVIDIA's model serving runtime. Handles TensorRT/ONNX/TorchScript. Dynamic batching across concurrent requests. Production-scale at >1000 req/s.
Our FastAPI /api/v1/prediction/{event_id} scores 3 route options in under 1ms. Triton's deployment overhead (GPU server, model repository, gRPC client) would cost more than the rest of the pipeline combined. FastAPI is correct.
Metabase vs Streamlit
Metabase — no-code BI builder for non-technical stakeholders. SQL questions → charts. Requires its own Docker service + PostgreSQL metadata store.
Streamlit — Python-code dashboard. Full control over layout, ML panels, and 60s live refresh. No extra SQL layer. Correct for a developer-owned single-user project. Metabase adds infrastructure for zero benefit here.
Feature Store — what it solves (and why we don't need one)
A Feature Store centralises engineered features so multiple teams and models share consistent definitions — preventing training-serving skew at scale.
We have one model and one engineer. Features are computed inline in the SQL training query. A Feature Store (e.g. Feast, Hopsworks) would add a registry, a serving layer, and a separate service — to avoid a problem we don't have. Would become necessary if the project grew to 10+ models across multiple teams.

Resume Bullets — Copy These
  • Pipeline Design Built an end-to-end data pipeline driven by Google Calendar (OAuth2) — ingesting real-time transport data from LTA DataMall (v3/BusArrival), OneMap routing API, and Singapore's weather API — storing structured data in DuckDB across a typed nine-table schema that includes ML predictions and pipeline monitoring.
  • SQL Transformation Designed a SQL transformation layer joining route options, weather forecasts, and disruption alerts; implemented window-function-based route ranking with business rules (rain penalty, disruption buffer) to generate per-event commute recommendations.
  • Production Robustness Implemented exponential backoff retry on all API calls, idempotent upsert pattern (INSERT OR REPLACE), GPS coordinate validation, and a pipeline_runs monitoring table — making the pipeline safe to run in production.
  • Data Serving API Designed a REST API serving layer with FastAPI exposing commute recommendations as a queryable endpoint with auto-generated Swagger documentation — decoupling the recommendation engine from any specific frontend.
  • ML Models Diagnosed target-proxy dominance in an initial duration model — the routing engine's own estimate carried 0.875 feature importance because the training target was itself largely derived from that baseline, so the model re-derived the schedule instead of learning contextual delay — and redesigned it to predict the residual delay over the baseline, cutting that feature to 0.041 and removing a hard prediction ceiling; engineered bus_headway_gap (next_bus2_mins − next_bus_mins) as a crowd-buildup signal feeding both a RandomForestRegressor for delay and a RandomForestClassifier for bus crowding, scoring all three route options individually, backfilling reconstructed outcome estimates that record their own reconstruction method, and evaluating 7-day MAE against both that outcome and a no-ML schedule baseline.
  • Orchestration & Infrastructure Authored an Apache Airflow DAG (7 tasks, 30-minute schedule, gate_evaluate ShortCircuitOperator gating ML evaluation to the single 08:00 SGT run by logical time); containerised the runtime with Docker Compose — pipeline, API, and dashboard as three services with volume-mounted persistent storage. The Docker pipeline service uses a custom scheduler.py with a 7-state adaptive machine (NO_EVENT → EVENT_DETECTED_BURST → WATCHING → LEAVE_WINDOW → IN_TRANSIT → ARRIVAL_VERIFY → POST_ARRIVAL_COOLDOWN) instead of a fixed sleep loop.
  • Data Architecture Implemented a two-layer storage design: a date-partitioned Parquet landing zone feeds a typed nine-table DuckDB analytical store. Schema is star-shaped around route_options as the central fact-like table, with a foreign key to the calendar event; weather, bus arrivals and train alerts join on natural keys and time windows rather than as conformed dimensions. Reference data is upserted in place (Type-1 overwrite), while live bus arrivals are deliberately append-only.
